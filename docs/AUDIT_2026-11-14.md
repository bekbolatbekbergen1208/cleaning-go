# Cleaning Go — повторный аудит, 14 ноября 2026

## Архитектура и границы проверки

Монорепозиторий: Next.js PWA (`apps/admin`), Expo/React Native (`apps/mobile`),
локальный Node HTTP API (`local/server.mjs`), общий HTTP-клиент
(`packages/local-client`), схемы валидации (`packages/validation`). Данные —
PostgreSQL через PGlite на диске (`local/database.mjs`), миграции и RLS —
`local/migrations`. В production Nginx направляет сайт в Next.js, а внутренний
API слушает loopback. Docker/Compose и ORM в текущем проекте нет.

В production проводились только безопасные GET и проверки отказа в доступе;
создание аккаунтов и заказов выполнялось только на изолированной базе.

HTTP-поверхность Next.js: `POST /api/auth/login`, `POST|OPTIONS /api/register`,
`POST /api/local/{api,upload}`, `GET /api/local/file`, `GET /api/company/tracking`,
`GET /api/orders/{id}/route`, `GET|POST|PATCH /api/orders/{id}/tracking`.
Внутренний API: `GET /health`, `GET /file`, `POST /upload`, `POST /api`;
действие последнего определяется полем `action` (query/RPC/auth/recovery/files).
Неизвестные методы/маршруты проверены на отказ. Публичный `POST /api/register`
покрыт CORS preflight; остальные browser mutation endpoints проверяют origin.

Маршруты интерфейса сгруппированы по ролям: публичные `/`, `/login`,
`/register`, `/reset-password`, `/admin/login`, `/r/{code}`; клиентские
`/profile`, `/profile/company`, `/profile/orders`, `/order/new`,
`/order/{id}/tracking`, `/order/{id}/review`; клинерские `/cleaner/my-work`,
`/cleaner/direct-orders`, `/cleaner/company-orders`; компания `/company`,
`/company/cities`, `/company/employees`, `/company/orders`, `/company/reports`,
`/company/sales`, `/company/tracking`; администрация `/admin`, `/users`,
`/orders`, `/companies`, `/communities`, `/services`, `/settings`,
`/moderation`, `/verifications`; общая страница уведомлений — `/notifications`.

## Исправлено в рабочем дереве

1. Публичный переход к заказу и защищённые маршруты больше не отправляют
   браузер на `localhost:3020`; редирект использует публичный origin.
2. Клиент после успешного создания заказа попадает в список заказов, а не
   остаётся на форме с возможностью повторить отправку. Добавлена синхронная
   блокировка двойного submit до перехода/ошибки.
3. Ошибки форматов UUID услуг/опций в мобильной валидации устранены; исправлены
   проверка невозможной даты и защита от повторного заказа на мобильном.
4. Протокол подтверждения цены проверяет версию предложения; устаревшая форма
   не может подтвердить новую цену. Исправлена обработка таймаута HTTP-ответа и
   загрузки фото.
5. Web/mobile интерфейс восстановления пароля больше не обещает отправленное
   письмо: backend сейчас сохраняет ссылку в локальную очередь файлов, SMTP
   не подключён. Мобильный экран корректно завершает loading при ошибке сети.
6. Ограничение частоты web-запросов больше не доверяет клиентскому префиксу
   `X-Forwarded-For`. Nginx production уже перезаписывает адрес клиента и
   успешно прошёл `nginx -t`; исходный конфиг сохранён для отката.

## Подтверждённые сценарии

- Next.js production build; TypeScript и линтер web/mobile — успешно.
- 17 Node-тестов и 10 тестов валидации — успешно.
- 132 HTTP/security/role-проверки: публичные и закрытые страницы, регистрация,
  вход/выход, cookies, CSRF/CORS, 400/401/403/404/409/415/429,
  неавторизованный доступ к GPS/файлам, подмена forwarded IP.
- 71 функциональная HTTP-проверка на изолированном сервере: 5 регистраций,
  4 заказа; компания, клинер, клиент и администратор; утверждение компании и
  клинера; цена и устаревшее предложение; назначение, GPS, фотоотчёт,
  завершение, отзыв и модерация; бонусы, отмена, спор, pending-карта,
  восстановление пароля и инвалидирование старой сессии.
- Браузер: 55 проверок страниц/действий на desktop и mobile в предыдущем
  проходе, без ошибок JS и горизонтального переполнения; дополнительно в этом
  проходе проверены мобильный экран отзыва, публикация через UI, переход и
  ровно одна запись в БД.
- Публичный production `/order/new` возвращает 307 на публичный `/login`, а
  не на localhost. Публичные страницы возвращают 200, закрытые API — 401.

## Сценарий клиента

Главная → «Заказать уборку» → вход/регистрация → выбор города и одобренной
компании → форма заказа (услуга, адрес на карте, время, фото) → «Мои заказы» →
согласие с ценой компании → отслеживание статуса и клинера → подтверждение
выполнения → отзыв. Если одобренных компаний нет, интерфейс сообщает, что
заказ пока недоступен. Для независимого клинера сценарий цены компании
пропускается. Карточная оплата без подключённого провайдера остаётся pending.

## Оставшиеся ограничения

- На production нет подключённой автоматической отправки писем: ссылка
  восстановления не доставляется пользователю. Нужны SMTP/почтовый провайдер
  и отдельный E2E-тест доставки.
- Реальный эквайринг, push/SMS и внешний маршрутизатор OSRM не проверены с
  рабочими провайдерами. Реальное Android-устройство, фоновый GPS и APK не
  тестировались в этом проходе.
- На последней проверке production-маркетплейс не имел одобренных компаний:
  реальный клиент пока не сможет оформить заказ, хотя изолированный полный
  сценарий работает.
- Кодовые изменения этого аудита находятся в рабочем дереве и **не выложены**
  на production; отдельно применено только исправление Nginx для заголовка IP.

Аудит подтверждает перечисленные проверки, но не гарантирует отсутствие всех
ошибок на каждом устройстве и при каждой внешней интеграции.
